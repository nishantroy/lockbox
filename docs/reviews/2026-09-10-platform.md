# Platform verification — 2026-09-10

Read-only Luna research agent; parent independently fetched Apple's `intervalTooShort` documentation JSON and confirmed its explicit fifteen-minute minimum. No physical-device experiments performed. These are API contracts, not evidence that the phone has automatically released restrictions.

## Findings

### DeviceActivity interval limits

Apple’s current documentation is explicit:

- **Minimum interval: 15 minutes** — [`MonitoringError.intervalTooShort`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror/intervaltooshort)
- **Maximum interval: one week** — [`MonitoringError.intervalTooLong`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror/intervaltoolong)

Therefore, the existing comment that short one-off schedules are merely “unreliable” is imprecise: schedules below 15 minutes are rejected with `intervalTooShort`. This does **not** establish callback timing or automatic-release reliability for longer intervals.

`startMonitoring` can also throw for invalid date components, unauthorized access, excessive activities, or tightly scheduled activities:

- [`startMonitoring(_:during:events:)`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:))

### Registration inside an active interval

Apple documents that if the current date is inside the schedule interval, `intervalDidStart(for:)` may be invoked immediately when monitoring begins:

- [`DeviceActivitySchedule.init`](https://developer.apple.com/documentation/deviceactivity/deviceactivityschedule/init(intervalstart:intervalend:repeats:warningtime:))
- [`startMonitoring`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:))

However, Apple also states that interval callbacks are invoked only when the device is in use:

- [`intervalDidStart(for:)`](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor/intervaldidstart(for:))
- [`intervalDidEnd(for:)`](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor/intervaldidend(for:))
- [`DeviceActivityCenter`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter)

Do not promise a callback exactly at the wall-clock boundary while the device is idle.

### Querying actual registered schedules

These APIs are available from iOS 15, and therefore from an iOS 17 deployment target:

```swift
let center = DeviceActivityCenter()
let names = center.activities
let registeredSchedule = center.schedule(for: activityName)
```

- [`activities`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/activities) returns activities currently monitored by the app’s extension.
- [`schedule(for:)`](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/schedule(for:)) returns the registered schedule, or `nil` if none is currently monitored.
- The returned schedule is a **static snapshot**; fetch it again to observe later changes.
- [`nextInterval`](https://developer.apple.com/documentation/deviceactivity/deviceactivityschedule/nextinterval) reports the current interval if one is ongoing, otherwise the next interval. It does not prove that a callback ran or that Managed Settings was applied.

`startMonitoring` with an existing activity name overwrites that activity’s prior schedule and events. `stopMonitoring([])` stops all activities, while named stopping ignores names that are not currently monitored.

## iOS 17 availability issue

The installed SDK is **iPhoneOS 26.5**, with Xcode 26.6. API-digester and Apple documentation report:

- `DeviceActivityCenter`, `DeviceActivitySchedule`, registration/query APIs, and monitor callbacks: **introduced iOS 15.0**
- `AuthorizationStatus.approved`: **introduced iOS 15.0**
- `AuthorizationStatus.approvedWithDataAccess`: **introduced iOS 26.4**

Citation: [`approvedWithDataAccess`](https://developer.apple.com/documentation/familycontrols/authorizationstatus/approvedwithdataaccess)

A direct unguarded expression using `.approvedWithDataAccess` fails when compiled for iOS 17:

```text
'approvedWithDataAccess' is only available in iOS 26.4 or newer
```

The current project build succeeds because the case appears in a `switch` pattern, but this was compiled against the 26.5 SDK—not an actual iOS 17 SDK. Any direct comparison, assignment, or use outside a suitable availability context requires `if #available(iOS 26.4, *)`. An older SDK that predates the case will not know the symbol at all.

This status is only needed for non-tokenized activity data. Normal tokenized Family Controls authorization uses `.approved`; the project does not use `FamilyActivityData`.

## Focused R1 integration checks

1. **Registration inside active window**
   - Register a schedule while the current time is inside it.
   - Immediately query `activities` and `schedule(for:)`.
   - Log whether `nextInterval` is current.
   - Keep the device in use and record whether/when `intervalDidStart` arrives.
   - Do not treat successful registration or `nextInterval` as proof of shielding.

2. **Recurring/manual exclusion**
   - With the recurring activity registered, attempt the manual/test lock.
   - It should be rejected or explicitly serialized; it must not overwrite the schedule or clear its Managed Settings policy.
   - Test the inverse: manual/test ownership must prevent recurring registration until resolved.

3. **Delayed callback enabled guard**
   - Disable or replace the schedule, then inject a late `intervalDidStart` into the monitor adapter.
   - Verify the callback checks persisted enabled state, activity name, configuration revision, and selection validity before applying policy.
   - Apple does not document stale delayed callbacks as a guarantee; treat this as hostile-input testing, not an observed platform contract.

4. **Invalid selection**
   - Test empty selections, allow-only selections with no application tokens, unknown mode values, corrupt shared data, and missing App Group data.
   - App-side validation and monitor-side validation must agree.
   - Invalid data must not produce `.all(except: [])` or silently fall into allow-only behavior.
   - Record an operational error and avoid applying a new broad policy.

## Unresolved constraints

- Callback delivery is usage-dependent; exact scheduled start/end latency remains device behavior requiring real-device evidence.
- `activities` and `schedule(for:)` expose registration state, not callback delivery or Managed Settings enforcement state.
- No local iOS 17 SDK is installed here; iOS 17 compatibility was checked only by compiling an iOS 17 deployment target against the iOS 26.5 SDK.
- No device schedules were changed, no deployment was performed, and the repository was not edited.
