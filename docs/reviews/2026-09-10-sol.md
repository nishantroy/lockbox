## MVP readiness verdict

**Not ready for bedtime MVP use.** The repository is a useful feasibility prototype, and the reported device QA establishes that immediate category deny/allow, persistence, and one scheduled-start/manual-disable path can work. It does **not** yet implement the lifecycle guarantees described in the plans:

- Active restrictions have immediate in-app bypasses.
- “Lock now” has no finite automatic end.
- Scheduled, manual, and test locks overwrite and clear one shared policy without overlap tracking.
- The recovery reducer is not connected to either process.
- Invalid live selection can produce an empty allowlist.
- Operational status is inferred from local flags and can be misleading.
- Natural scheduled release remains untested.

No files were modified, and no build, tests, or device operations were run during this read-only review.

## Verified defects

### P0 — Active scheduled restrictions can be cleared immediately

**References:**
`PhoneLockbox/ContentView.swift:174-177`
`PhoneLockbox/ScreenTimeCoordinator.swift:206-220`
`docs/interaction-design.md:65`

“Clear prototype lock” is always available on the configured dashboard. It calls `clearAllSettings()` without determining whether the store currently represents a test, manual, or scheduled lock. “Disable recurring schedule” also stops monitoring and immediately clears the active policy.

**Reproduction**

1. Let the scheduled interval start.
2. Open Phone Lockbox.
3. Tap **Clear prototype lock**, or **Disable recurring schedule**.
4. This app’s shared Managed Settings store is cleared before the scheduled end.

The supplied device QA’s scheduled-start/manual-disable result provisionally confirms this early-clear path works.

**Impact**

This directly violates active-rule protection and makes the current restriction an immediate ordinary-settings bypass.

**Fix/tests**

- Remove unrestricted clear controls from production UI.
- Persist a bounded occurrence and route all release operations through the lifecycle reducer.
- During an active occurrence, disabling recurrence should affect future occurrences only.
- Test scheduled lock → clear/test/disable controls, including force-quit and relaunch, and verify no path releases before recovery confirmation or natural end.

### P0 — A configured allow-only schedule can attempt to shield with an empty allowlist

**References:**
`PhoneLockbox/ScreenTimeCoordinator.swift:25-29,55-62`
`PhoneLockbox/ContentView.swift:27-31,161`
`Extensions/DeviceActivityMonitor/MonitorExtension.swift:20-32`

`canApplySelection` protects setup and immediate-lock buttons, but the dashboard picker remains editable after registration and writes every picker mutation directly to shared defaults. The monitor extension does not repeat validation. In allow-only mode it applies:

```swift
.applicationCategories = .all(except: selection.applicationTokens)
.webDomainCategories = .all(except: selection.webDomainTokens)
```

An unknown/corrupt mode also falls into allow-only because every value other than `"blockSelected"` enters the `else` branch.

**Reproduction**

1. Configure allow-only with at least one app and save the schedule.
2. Reopen the picker from the dashboard.
3. Deselect all applications, or leave only a website/category state with no expanded app tokens.
4. At the next callback, the extension applies `.all(except: [])`.

**Impact**

The code requests maximally broad application/domain shielding, subject to iOS exclusions, rather than reporting invalid configuration. This is a critical-access safety risk. The successful category QA does not exercise this empty-selection path.

**Fix/tests**

- Store one versioned, validated configuration blob rather than independently mutable fields.
- Require an exact recognized mode and a valid selection in the extension.
- On invalid/corrupt configuration, avoid applying a new broad policy and record an operational error for the app.
- Stage picker edits and commit only on explicit confirmation; support cancellation.
- Add extension-policy tests for empty app/domain sets, category-only selections, unknown modes, and corrupt data.

### P0 — “Lock now” and the prototype test are not bounded sessions

**References:**
`PhoneLockbox/ContentView.swift:103-117,162`
`PhoneLockbox/ScreenTimeCoordinator.swift:165-203`
`docs/product-plan.md:39`

Both paths directly assign shields. They persist no start, end, origin, policy snapshot, or scheduled release. The comment calling the prototype restriction “bounded” is inaccurate; it remains until some unrelated clear/end operation runs or the user manually clears it.

**Reproduction**

Tap **Lock now** outside the scheduled interval, then terminate the app. There is no occurrence end or one-off monitor registration that guarantees release at a confirmed future instant.

**Impact**

A manual restriction can remain indefinitely, or be released accidentally by another lifecycle event. The UI also provides no end-time confirmation.

**Fix/tests**

Resolve and confirm a finite end, persist the manual occurrence before applying policy, and schedule/reconcile its release. Test app termination, reboot, overlap with bedtime, repeated “Lock now,” and failure during persistence/application.

### P1 — Scheduled, manual, and test locks overwrite one another and clear prematurely

**References:**
`PhoneLockbox/ScreenTimeCoordinator.swift:37,180-207`
`Extensions/DeviceActivityMonitor/MonitorExtension.swift:7,10-39`

Every path uses the same named `ManagedSettingsStore("phone-lockbox")`. Applying an immediate lock replaces fields needed by a scheduled lock; `intervalDidEnd` then unconditionally clears the store even if a later manual/test lock should remain active.

**Reproduction**

1. Start a scheduled interval.
2. Press **Lock now** or start a test lock with different selections.
3. At the scheduled interval end, `intervalDidEnd` clears all policy, regardless of the immediate lock’s intended lifetime.

The inverse is also possible: an immediate action can weaken or replace the scheduled policy.

**Impact**

Overlap cannot obey “remain restricted until every applicable unreleased occurrence ends.”

**Fix/tests**

Model all active occurrences and reduce them to one effective conservative policy. End callbacks should expire only the matching occurrence and then re-evaluate the union. Test manual/scheduled overlaps in both start orders and all end orders.

### P1 — The documented session/recovery state machine is unused

**References:**
`PhoneLockbox/Policy/LockboxPolicy.swift:90-100`
`PhoneLockbox/ScreenTimeCoordinator.swift:40-48,122-224`
`Extensions/DeviceActivityMonitor/MonitorExtension.swift:10-39`

The comment says `LockboxSessionController` is used by app and extensions, but source references exist only in tests. Neither process persists sessions, recovery requests, released occurrences, policy revisions, or pending configuration. There is no recovery UI.

**Impact**

Duplicate/out-of-order callbacks, recovered-occurrence suppression, active-policy snapshots, pending relaxations, and crash recovery are absent. Passing reducer tests do not improve runtime behavior.

**Fix/tests**

Move the state model into code shared by the app and monitor, persist transitions before Managed Settings mutations, and make both processes reconcile idempotently. Integrate the delayed recovery flow before calling this an MVP.

### P1 — Registration, authorization, and enforcement status are misleading

**References:**
`PhoneLockbox/ScreenTimeCoordinator.swift:31,107-108,134-161`
`PhoneLockbox/ContentView.swift:22-23,145-157`

`saveConfiguration` marks setup complete before schedule registration. `scheduleIsRegistered` is memory-only and initializes to `false`; registration errors are not persisted. Both “Bedtime schedule active” and “Schedule saved” use a green check. After authorization is revoked, foreground refresh changes only the authorization row while the green success headline remains.

**Reproduction**

- Force registration to fail: the app still enters the configured dashboard.
- Relaunch: the error disappears and a green “Schedule saved” remains.
- Revoke authorization: the dashboard can simultaneously show a green schedule headline and “Denied.”

**Impact**

The user cannot distinguish saved intent, last successful registration, current authorization, or known policy-application failure.

**Fix/tests**

Persist structured operational status separately from configuration. Reconcile registration through available system state where possible, label it as registration rather than verified enforcement, and show authorization failure as a dominant unavailable state. Test failed registration, relaunch, revocation, and restoration.

### P1 — Foregrounding does not reconcile active or stale policy

**References:**
`PhoneLockbox/ContentView.swift:22-23`
`PhoneLockbox/ScreenTimeCoordinator.swift:107-108`

On activation, the app only refreshes authorization. It does not determine whether an occurrence should currently be active, reapply missing policy, clear expired policy, or resolve partial transitions.

**Impact**

A missed/stale callback or policy cleared by another app path persists until a later Device Activity callback. Authorization restoration also has no defined resume behavior.

**Fix/tests**

Run the same pure reconciliation routine on app launch/activation and monitor callbacks. Test launch inside/outside an interval, stale shield after natural end, missing shield during an active occurrence, and authorization restoration.

### P1 — Active selection edits are neither frozen nor honestly represented

**References:**
`PhoneLockbox/ScreenTimeCoordinator.swift:25-29`
`PhoneLockbox/ContentView.swift:145-161`
`Extensions/DeviceActivityMonitor/MonitorExtension.swift:13-32`

Picker changes immediately replace the extension’s live configuration. There is no active baseline or pending revision. Meanwhile the dashboard immediately describes the new selection even though the currently applied Managed Settings policy may still be the old selection.

A duplicate/late callback would read the new values and could mutate an existing occurrence.

**Fix/tests**

Snapshot policy per occurrence, stage potentially relaxing edits for an explicit activation boundary, and display active versus pending rules separately. Test edits during both halves of overnight windows and stale callback replay.

### P2 — `nextOccurrence` inconsistently skips an occurrence that is already active

**References:**
`PhoneLockbox/Policy/LockboxPolicy.swift:131-149`
`CoreTests/LockboxPolicyTests.swift:21-27`

The function returns the current occurrence during an overnight morning tail, establishing current-or-next semantics. However:

- For `22:00–07:00` queried at `23:00`, it returns tomorrow’s start rather than the occurrence already active.
- For `09:00–17:00` queried at noon, it returns tomorrow.

**Impact**

If integrated into reconciliation, it would fail to recognize active evening and same-day sessions. The current runtime does not use this function, so this is latent rather than a present Device Activity failure.

**Fix/tests**

Define exact boundary semantics and explicitly handle `start <= now < end`. Add tests before start, at start, inside both interval shapes, at end, and after end.

### P2 — Recovery can complete after natural expiry, and arbitrary delays can bypass waiting

**References:**
`PhoneLockbox/Policy/LockboxPolicy.swift:66-73,102-123`

`confirmRecovery` checks only eligibility, not `date < session.end`. A pending recovery confirmed after the natural end becomes `.released` rather than `.expired`, contrary to “morning end wins.” The public event also accepts zero or negative delay, making eligibility immediate or earlier than the request.

**Fix/tests**

Validate a positive finite delay at the reducer boundary. On confirmation at or after `session.end`, expire the session instead of releasing it. Add exact-end, after-end, zero/negative delay, and persisted-corruption tests.

### P2 — Persistence failure creates split-brain app/extension state

**References:**
`PhoneLockbox/ScreenTimeCoordinator.swift:38,84-103,224-226`
`Extensions/DeviceActivityMonitor/MonitorExtension.swift:8,13-17`

The app silently falls back to `.standard` if the App Group suite cannot open, while the monitor keeps an optional App Group store. The app can therefore report saved/configured state that the extension cannot read. Decode/encode failures are also silently reset or ignored, with no schema version or corruption status.

**Fix/tests**

Treat App Group unavailability as a surfaced operational failure; do not fall back to process-local defaults. Persist a versioned validated blob and test missing entitlements, malformed data, migration, and interrupted writes. The checked-in app and monitor App Group entitlement strings do match at `PhoneLockbox/PhoneLockbox.entitlements:7-10` and `Extensions/DeviceActivityMonitor/PhoneLockboxMonitor.entitlements:7-10`.

## Platform hypotheses and required device validation

These are **not verified defects**:

1. **Natural scheduled end:** `Extensions/DeviceActivityMonitor/MonitorExtension.swift:36-39` is the only automatic scheduled cleanup path. The reported test covered scheduled start followed by manual disable; it did not establish a natural end with the app closed. Test exact observed release time foregrounded, backgrounded, force-quit, and after reboot.

2. **Registration inside an already-active window:** `ScreenTimeCoordinator.swift:154-157` assumes the start callback will apply policy. The UI does not offer “start now” versus “next occurrence.” Establish actual callback behavior before promising either outcome.

3. **DST/time-zone behavior:** Runtime scheduling delegates hour/minute components to `DeviceActivitySchedule`; the pure calendar helper is not integrated and does not encode an explicit skipped/repeated-time policy. Test spring gaps, repeated hours, time-zone changes before a window, and changes during an active window. An active session currently has no frozen absolute end.

4. **Cross-process visibility/order:** App Group persistence worked in the supplied force-quit checks, but immediate registration after multi-key writes and concurrent callback/edit ordering remain untested.

5. **Category and browser coverage:** Immediate category deny/allow reportedly worked. Separately test category-derived websites and browser paths: block-selected sets `webDomainCategories = nil` at `ScreenTimeCoordinator.swift:196` and `MonitorExtension.swift:25`, so app-category success does not establish category website behavior.

6. **Authorization revocation/restoration and reboot:** Confirm actual Managed Settings persistence and callback behavior; do not infer it from the authorization enum alone.

7. **Policy application status:** Managed Settings assignments are treated as success and the UI says “Apps are blocked now.” Device tests can establish observed outcomes, but the app should still distinguish “application attempted” from independently verified global enforcement.

The repository comment asserting a minimum scheduled interval at `PhoneLockbox/ScreenTimeCoordinator.swift:165-167` should be backed by current official documentation or recorded SDK/device evidence rather than treated as an established limit.
