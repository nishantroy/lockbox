## Original blocking findings (resolved for R1)

1. **Registration can look healthy while OS retains the previous schedule**  
   `PhoneLockbox/ScreenTimeCoordinator.swift:207-225, 354-355`  
   `recurringEnabledIntent` is committed before `startMonitoring`, while reconciliation checks only that an activity exists—not that its interval matches the persisted revision.  
   **Repro:** OS has 23:00–06:00; save 22:00–07:00; terminate after line 219 but before line 222. Relaunch shows registered. The old 23:00 callback applies the new policy, while the old 06:00 end is rejected as early by `RuntimeScheduleDecision`; no 07:00 callback exists, potentially leaving shielding indefinitely.  
   **Fix:** Persist separate registration-attempt/armed revision state and compare the queried `DeviceActivitySchedule` components with the saved configuration. Treat mismatches as unarmed and explicitly stop/re-register.

2. **Emergency reset races monitor callbacks and can erase state while leaving shielding active**  
   `PhoneLockbox/ScreenTimeCoordinator.swift:295-304`  
   `Shared/RuntimeStore.swift:68-77`  
   `Extensions/DeviceActivityMonitor/MonitorExtension.swift:38-56`  
   Stop and `clearAllSettings()` occur outside the file lock. A monitor callback can hold the lock, commit apply intent, then apply after the app clears; reset subsequently deletes its JSON. Result: monitoring stopped, state gone, restrictions active.  
   **Fix:** Under one shared lock, persist a reset/tombstone generation that disables callbacks, stop monitoring, clear settings, then retain an empty document. Any queued callback must re-read and reject that generation.

3. **Persisted policy intents are never reconciled after interruption**  
   `MonitorExtension.swift:48-56, 86-94`  
   `ScreenTimeCoordinator.swift:242-260, 316-327, 358-367`  
   Nothing reads `policyIntent`; tests prove only that it survives. Terminating the extension after committing `.clear` but before `clearAllSettings()` leaves restrictions beyond natural end, and foregrounding does not retry cleanup. Similarly, an interrupted `.apply` leaves ownership set, causing duplicate starts to be rejected without applying policy.  
   **Fix:** Add bounded launch/foreground/callback reconciliation: replay `.clear`; for `.apply`, revalidate authorization, selection, revision, and current civil window, then apply or expire/clear. Add injected crash-point tests.

4. **Displayed bedtime can differ from what Save registers**  
   `PhoneLockbox/ContentView.swift:10-27, 176-180, 214`  
   `ScreenTimeCoordinator.swift:303-307`  
   `startTime`/`endTime` initialize once, while Save passes coordinator values. After emergency reset—or a failed draft persistence—the UI can still display the old times while Save registers coordinator defaults.  
   **Fix:** Use one source of truth: bind pickers directly to coordinator draft times, or resynchronize after reset/failure and save the displayed values.

5. **First-launch legacy migration is not atomic with runtime-file discovery**  
   `ScreenTimeCoordinator.swift:77-83, 379-414`  
   `hasDocument` is checked outside the store lock. A legacy registered callback can create a diagnostic-only JSON before migration, causing migration to be skipped; if it appears between the check and transaction, migration overwrites it.  
   **Fix:** Implement a locked load-or-migrate transaction with an explicit migration marker and defined handling for extension-created empty documents.

6. **Lock timeout uses adjustable wall time**  
   `Shared/RuntimeStore.swift:109-120`  
   Confirmed: moving the clock backward can extend the nominal 0.5-second wait indefinitely; moving it forward causes premature timeout. This is unsafe for an extension with bounded execution time.  
   **Fix:** Use `ContinuousClock` or `DispatchTime` for elapsed timeout measurement.
