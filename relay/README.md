# Phone Lockbox R5 companion relay (`relay/`)

TypeScript port of the R5 companion protocol's server side: the
authorization semantics of `InMemoryCompanionRelay`
(`CompanionKit/Sources/CompanionKit/InMemoryRelay.swift`) combined with the
durability semantics of `CompanionRelayService`
(`CompanionRelayService/Sources/CompanionRelayService/DurableReducer.swift`,
`DurableRelay.swift`, `DurableStore.swift`), backed by Postgres instead of
an in-memory store. See `docs/r5-relay-plan.md` for the approved plan and
`docs/companion-prototype.md` / `docs/companion-security.md` for the
protocol/checkpoint background.

This is a local-first prototype. It runs locally today; the eventual target
is Vercel Hobby + Vercel Marketplace Postgres (Neon). No deployment has
happened as part of this work — see "Out of scope" below.

## Quick start

```sh
cd relay
npm install
npm run db:start          # Postgres 16 in Docker, bound to 127.0.0.1:56330
npm run db:migrate
npm run dev                # relay on http://127.0.0.1:8002
npm test                   # vitest, against the same local Postgres
npm run typecheck
npm run db:stop
```

Works from a clean checkout with no `.env` needed: `db:migrate`/`dev`/
`retention:purge` (and the test suite) default `DATABASE_URL` to the local
Postgres above (`src/db.ts`'s `resolveDatabaseURL`) whenever
`NODE_ENV !== "production"`, printing a one-line notice to stderr when they
do. **Production must still set `DATABASE_URL` explicitly** -- the default
never applies when `NODE_ENV=production`. Copy `.env.example` to `.env` to
override any of these locally (loaded via `--env-file-if-exists`, so its
absence is not an error).

Ports are reserved in `/Users/nishantroy/code/AGENTS.md`'s local HTTP port
registry: the dev server on **127.0.0.1:8002**, Postgres on
**127.0.0.1:56330**. Both bind to loopback only. Before starting either,
check `lsof -nP -iTCP:8002 -sTCP:LISTEN` / `:56330`.

## Layout

- `api/v1/{operations,inbox,health}.ts`, `api/v1/invite/lookup.ts` (pairing v3 token lookup) — Vercel Node functions (Web
  `Request -> Response` signature). Thin wrappers over `src/handlers.ts`.
- `api/cron/retention-purge.ts` — the daily Vercel Cron target
  (`vercel.json`); authenticated with `Authorization: Bearer $CRON_SECRET`,
  the same convention Vercel Cron itself uses.
- `scripts/dev-server.ts` — a plain `node:http` server exposing the same
  handlers locally, so local development needs no Vercel CLI/login.
- `scripts/migrate.ts`, `scripts/retention-purge.ts` — one-shot CLI runners.
- `src/canonical.ts` — port of `CompanionCanonical` (canonical byte framing,
  SHA-256 digest, base64url, the Foundation `Date`/`Data` wire encodings,
  the `PairingAcceptance.code(invite:approver:)` verification-code
  derivation).
- `src/crypto.ts` — Ed25519 sign/verify using only Node's built-in
  `node:crypto` (no third-party crypto dependency), via RFC 8037 JWK import
  for raw 32-byte keys. CryptoKit's `Curve25519.Signing` is Ed25519 with
  32-byte raw keys, so seeds/public keys are byte-identical across Swift and
  Node.
- `src/protocol.ts` — the wire-level protocol types (`DeviceIdentity`,
  `Invitation`, `Pairing`, `TrustedRequest`, `Approval`, `SignedOperation`,
  `RelayResult`/`RelayResponse`/`InboxResponse`, ...), their decoders, and
  their signature verification, all ported field-for-field from
  `CompanionKit`/`CompanionRelayService`'s Swift `Codable` structs.
- `src/ledger.ts` — the per-owner protocol state shape (port of
  `DurableOwnerLedger`) and its Buffer-safe JSON (de)serialization for
  Postgres storage.
- `src/reducer.ts` — the pure protocol reducer (port of
  `DurableProtocolReducer.apply`), the closed operation allowlist, and the
  per-signer rate limiter (port of `InMemoryCompanionRelay.charge`).
- `src/db.ts` — Postgres access: migrations, the owner-row lock/transaction
  primitives, the operation log, the cross-owner pairing index, and the
  global per-signer rate limiter.
- `src/service.ts` — orchestration (port of `DurableRelayService.submit`):
  decode, resolve+lock the owner partition, idempotency replay, authorize,
  check `expectedRevision`, run the reducer, commit.
- `src/retention.ts` — the 30-day retention purge job.
- `src/handlers.ts` — the shared Web `Request -> Response` handlers used by
  both `api/v1/*.ts` and `scripts/dev-server.ts`.
- `migrations/001_init.sql`, `migrations/002_review_fixes.sql`,
  `migrations/003_retention_cursor.sql`, `migrations/004_invite_token.sql` (pairing v3 hashed-token index) — schema.
- `test/fixtures/vectors.json` — golden vectors generated by
  `CompanionKit/Sources/CompanionVectorGen` (see below).
- `test/fixtures/error-codes.json` — the pinned error-code list (see
  "Error codes").

## Canonical/crypto parity with Swift

`CompanionKit/Sources/CompanionVectorGen` is a small Swift executable target
added to `CompanionKit/Package.swift` (no existing CompanionKit source file
was modified). It writes deterministic fixtures — fixed Ed25519 test keys,
every operation kind's canonical signing bytes/signature/full JSON (both the
enveloped reference form and the *actual* wire form real clients send), the
`Date`/`Data` wire-encoding samples, the verification-code derivation, and
Swift's synthesized `RelayResult` enum JSON shape — to
`relay/test/fixtures/vectors.json`. Regenerate after any protocol change:

```sh
swift run --package-path CompanionKit CompanionVectorGen "$(pwd)/relay/test/fixtures/vectors.json"
```

`test/vectors.test.ts` verifies every vector byte-for-byte and asserts that
tampered/cross-domain/wrong-key variants are rejected.

### Wire format

Both the sync `CompanionClient` and the new async HTTP client
(`CompanionKit/Sources/CompanionKit/ProtocolModels.swift`) send
`SignedOperation.body` as the **raw, per-kind payload** (Invitation,
TrustedRequest, Approval, ...) — there is **no** `DurableOperationEnvelope`
wrapper on the wire, despite that type existing in
`CompanionRelayService/Sources/CompanionRelayService/DurableOperation.swift`
as a reference/test helper. `expectedRevision` is sent as-is and is often
`null` ("no optimistic check"); a non-null value is still enforced. This
relay decodes `operation.body` directly as the command payload and uses
`operation.expectedRevision` directly. `test/fixtures/vectors.json`'s
`rawOperations` array holds vectors in this actual format (including one
with a non-null `expectedRevision`); `operations` holds the enveloped
reference form for completeness.

JSON *key order* does not need to match Swift's `.sortedKeys` output — JSON
objects are unordered and decoding doesn't care. What must match
byte-for-byte is the canonical *signing field* framing (ported in
`canonical.ts`) and the `Date`/`Data` wire *values*: `Date` encodes as
seconds since the 2001-01-01 reference date (Foundation's default `Codable`
behavior, not ISO-8601 or Unix-epoch seconds) and `Data` encodes as standard
base64 (not base64url).

## Response anchoring (`stateRoot` / `ownerIdentityID`)

`POST /v1/operations` always returns `ownerIdentityID` and `stateRoot` on
success:

- `ownerIdentityID` is the identity of the ledger the operation **mutated**
  — never simply the signer. For an owner-signed operation that's the
  signer; for a helper-signed operation (`accept`, a `consent` accept,
  `approval`) it's the *other* person's owner ID, resolved before the owning
  transaction begins (via the acceptance/mutation's embedded owner identity,
  or via `companion_approver_pairing` keyed by `pairingID` for `approval`,
  since `Approval` carries no owner identity of its own).
- `stateRoot` is the canonical root of **that owner's ledger state only**
  (`computeStateRoot` in `src/service.ts`) — never a whole-database hash.
  Hashing every owner partition (as
  `DurableRelayDatabase.canonicalStateRoot()` does in the Swift reference)
  would make one owner's write change every other owner's reported root, so
  an unrelated owner's client would see false "conflicting root"
  rejections. This root is TS-internal: it does not need to match the Swift
  reference's byte layout, only to be a deterministic, collision-resistant
  function of exactly one owner's ledger + revision, computed as
  `SHA-256(canonicalFrame(domain, [revision, JSON(ledger)]))`.

`POST /v1/inbox` populates `ownerIdentityID`/`stateRoot` **only** when the
signer is an owner fetching their own single ledger (anchoring is
well-defined there); both fields are **omitted** for a trusted approver's
inbox fetch, since that can span several owners' ledgers with no single
well-defined anchor, and the client does not anchor when they're absent.
Every inbox response (owner or helper) also includes `pairings` (every
pairing where the signer is the owner or the approver, including revoked
ones still within the retention window) and `consents` (the current
`RelationshipConsent`, with its generation, for each of those pairings) —
`Pairing`/`RelationshipConsent` are encoded with the exact Swift `Codable`
field shapes.

## Reducer port and Postgres transaction

Every request is charged against a global, DB-backed, fixed-window rate limit
(`src/db.ts`'s `chargeGlobalRateLimits`, each subject its own implicit
single-statement transaction) *before* any owner partition is resolved or
locked. It charges **two subjects**: `signer:<identityID>` and, when the HTTP
layer resolved one, `ip:<address>` (from `x-forwarded-for`'s first hop --
Vercel sets this at the edge; `scripts/dev-server.ts` sets it from the raw
socket address for local dev, so `src/handlers.ts` reads it the same way
either way). *Every* listed subject is charged unconditionally, and the
request is allowed only if *all* of them are still within budget -- so an
attacker flooding from many identities behind one IP still drives that IP's
counter up (and gets blocked once it's over), and a shared-IP legitimate
signer isn't starved by a completely different signer's own separate budget.
This is what bounds e.g. a flood of `ack`s from freshly generated identities,
each of which would otherwise unconditionally create a new `companion_owner`
row before any per-owner limiter ever ran. Stale rows are purged once
`window_start < now - windowSeconds` (`purgeStaleRateLimits`, called from
retention on every run) -- a fixed-window counter's row is meaningless once
its window has elapsed, which has nothing to do with the unrelated 30-day
data-retention policy. The relay then runs the mutation in one Postgres
transaction (`src/db.ts`'s `lockOwnerRow`/`saveOwnerRow`, invoked from
`src/service.ts`):

1. `SELECT ... FOR UPDATE` locks (creating if absent) the owner's ledger row.
2. The stored `state_root` is recomputed and compared against the loaded
   state; a mismatch fails closed (`integrity_error`, a 500-class error --
   this indicates the durable record may itself be corrupt, not that the
   caller's request was malformed) rather than proceeding on possibly-tampered
   state. `POST /v1/inbox`'s owner-fetch path and the retention purge job
   (`purgeOwner`, before pruning/re-rooting anything) verify the same way.
3. An idempotent replay of an already-committed `operationID` (same signer,
   kind, `expectedRevision`, and body digest) returns the exact stored
   receipt, including its original `(revision, stateRoot)` — persisted
   per-operation (`companion_operation.state_root_after`) precisely so a
   replay doesn't report the ledger's *current* (possibly further-advanced)
   state. A resubmission that changes any of those four is an
   `idempotency_conflict`, not a silent replay.
4. Otherwise: the closed allowlist (`src/reducer.ts`'s `authorize`), the
   per-owner-ledger rate limiter (`chargeRateLimit`, a port of
   `InMemoryCompanionRelay.charge`), `expectedRevision` (when non-null), then
   the reducer itself, run against the locked in-memory ledger. Any
   unexpected exception while decoding/reducing the payload (unparseable,
   null, or otherwise malformed JSON for that operation kind) is caught and
   surfaced as 400 `malformed`, never allowed to escape as an uncaught
   exception the HTTP layer would turn into a 500.
5. The new state, state root, and a durable operation receipt commit
   together; `UPDATE ... WHERE revision = <locked revision>` guarded update
   means a losing concurrent writer's `UPDATE` affects zero rows and is
   surfaced as `stale_revision` (`test/race.test.ts` proves exactly one of
   two same-revision concurrent writers wins).

Every ID-keyed ledger map (`src/ledger.ts`) is a null-prototype object
(`Object.create(null)`), not a plain `{}`. Request/approval/session/pairing/
invitation/acceptance IDs are free-form, only length/whitespace-validated
strings from a signed payload, so a client could otherwise choose an ID like
`"__proto__"` and have a later `map[id] = value` bracket assignment silently
repoint the object's prototype instead of creating an ordinary own property.
`test/security-fixes.test.ts` and the ledger (de)serialization round-trip
both exercise this.

`src/reducer.ts` ports every `DurableProtocolReducer` case: invitations,
acceptance/confirmation (including the one-time verification-code check and
discarding every competing pending acceptance), consent grant/accept/revoke
with monotonic generations (and terminal invalidation of outstanding
authority on any generation change), sessions, requests (exact
session/active-set/pairing/consent-generation binding), one-of-N
first-accepted-wins approval, decline, cancel (rejecting a request whose
approval was already consumed), use (single-use, exact-binding consumption),
natural end, revoke, and `replace_pairing`. The closed allowlist
(`OWNER_ONLY_KINDS`/`APPROVER_ONLY_KINDS`) matches `DurableStore.swift`'s
`ownerSignedKinds`/`approverSignedKinds`, with one deliberate exception:
`accept` does not additionally require an already-active pairing at the
authorization-gate level (a trusted approver signs `accept` *before* any
pairing exists — `confirm` is what creates it), matching
`InMemoryCompanionRelay`'s own "accept" case, which checks only
`signer == acceptance.approver`. Every kind that *does* require an active
pairing/consent (approval, consent, use, requests) enforces that precisely
and contextually inside its own reducer case.

## Retention

`src/retention.ts` purges, 30 days after they become terminal: cancelled/
declined/expired requests (with their approvals and approval-use records --
including requests that simply lapsed without any later activity, whose
expiry the purge job computes itself rather than waiting for a lazy touch),
revoked pairings (together with their consent record and
`companion_approver_pairing` mapping — safe because a revoked pairingID is
a hash of a one-time-use inviteID and is never reissued), consumed or
expired invitations and their pending acceptances, ended sessions, used
consent/approval nonce and approval-ID markers, and per-identity rate-limit
entries that have gone wholly stale. The owner operation log
(`companion_operation`) and the global rate-limit table are purged on the
same 30-day window.

**Before pruning/re-rooting anything, `purgeOwner` verifies the stored
`state_root` against the loaded state**, exactly like the mutation and
owner-inbox-read paths do, and fails closed with `integrity_error` on a
mismatch (`test/review-round2.test.ts` covers all three paths, plus that an
uncorrupted root still passes on all three). **A purge that mutates a ledger
advances that owner's `revision` by exactly one and commits a synthetic
`retention_purge` operation-log receipt carrying the real new state root
(`newRoot`, not a placeholder)**, in the same transaction, exactly like a
client-submitted mutation would. This matters because the client-side
rollback anchor treats the same revision reported twice with two different
`stateRoot`s as a fork; since purging changes `stateRoot` (the pruned content
hashes differently) without this it would look exactly like a rollback/fork
to an honest client, and persisting the real root (not a placeholder) is what
makes that receipt actually useful if ever read back. A no-op purge (nothing
yet old enough) touches neither. `test/retention.test.ts` covers the exact
boundary (29 days 23:59:59 retained, 30 days 00:00:01 purged) for each record
kind, and the revision/receipt behavior for both the mutating and no-op cases.

The cron target (`api/cron/retention-purge.ts`) batches by both a wall-clock
budget (`maxDurationMs`, default 8s, under a Vercel Hobby function's default
10s timeout) and a persisted **owner-batch cursor**
(`companion_retention_cursor`, a single row holding the last fully-processed
`owner_id`): each invocation resumes just past that cursor in `owner_id`
order and wraps around to the start once it runs out, so successive daily
runs sweep through every owner over time instead of always reaching only the
same early-`owner_id` owners while later ones never get a turn.
`ownersRemaining` in the summary reports how many were left in *that* attempted
batch. A call with no `maxOwners` cap (tests, manual/local runs) ignores the
cursor entirely and processes every owner in one pass, leaving the cursor
untouched. `test/review-round2.test.ts` covers cursor advancement, wraparound,
and the no-cap case. `RETENTION_DAYS` is validated (finite, >= 1) before any
purge query runs.

**Accepted trade-off:** because the operation log is purged on the same
30-day window, a client retry of an `operationID` older than 30 days is no
longer idempotency-checked. This protocol's request/session lifetimes are at
most 7 days, so 30 days is comfortably longer than any legitimate retry
window.

## Consent replay and inbox freshness

Consent mutations (`grant`/`accept`/`revoke`) have no independent expiry
field the way an invite/session/request does, and their replay-nonce marker
is eventually purged by retention -- so without a bound, a captured old
signed mutation could be replayed (with a fresh operationID, once the
original's idempotency row and nonce marker are 30+ days gone) to re-grant a
scope that was since revoked. `src/reducer.ts`'s "consent" case therefore
also enforces a 24-hour maximum age on `issuedAt` (`CONSENT_MAX_AGE_SECONDS`),
in addition to the existing 60-second future-skew check every `issuedAt`
field in this protocol uses. `test/security-fixes.test.ts` includes a test
that reproduces the exact captured-old-grant-after-a-30-day-purge shape and
confirms it is rejected by this age check alone (i.e. even simulating that
the nonce/operation-log markers are already gone).

`POST /v1/inbox`'s query otherwise has no freshness or replay protection at
all (it is a read, not a mutation). The signed body accepts an `issuedAt`
(seconds since the Swift reference date, like every other timestamp field;
the key is omitted, not null, when absent — matching the Swift client's
actual encoding): when present, the relay enforces the same 60-second
future-skew bound plus a 5-minute maximum staleness
(`INBOX_FRESHNESS_WINDOW_SECONDS`). **`REQUIRE_FRESH_INBOX` defaults to
requiring the field** (both Swift clients always send it now); set it to the
exact string `"false"` to explicitly allow the legacy (`issuedAt`-less) form
during a transition/rollback. Inbox fetches are never written to the operation
log and never idempotency-checked/replayed — each fetch reads current
committed state directly; `test/security-fixes.test.ts` proves two
identical-body fetches straddling an intervening mutation return different
(current) results.

409-class respectively, distinct from `malformed`, since neither indicates a
problem with the caller's own request.

## Pairing routing security

`companion_approver_pairing.pairing_id` is the sole key an `Approval` (or an
approver's inbox fetch) can use to find its owner, since `Approval` carries
no owner identity of its own. `replace_pairing`'s `replacementPairingID` is
chosen by whichever client constructs the `PairingReplacement` proposal (the
*replacement approver's* device, per `PairingReplacement.propose` in
CompanionKit), so nothing stops it from colliding with a `pairing_id` an
unrelated owner already claimed. `db.ts`'s `recordApproverPairing` closes
this: claiming a `pairing_id` that already exists under a *different* owner
fails the whole transaction (`pairing_conflict`) rather than silently leaving
the index pointing at whichever owner claimed it first (which used to
misroute the other owner's approvals/inbox to the wrong ledger). A same-owner
re-insert is a harmless no-op. Retention's cleanup of a purged pairing's
routing row is scoped by owner (`deleteApproverPairing`), so it can never
remove a different owner's row even if a collision were somehow forced.
`test/security-fixes.test.ts` covers both the live collision attempt and the
scoped-delete half of the fix directly against the index.

## Vercel deployment shape (not yet deployed)

- `api/v1/{operations,inbox}.ts` export a named `POST` handler and
  `api/v1/health.ts` a named `GET` handler (the current Vercel Node runtime
  convention), each with the Web `Request -> Response` signature.
- `vercel.json` rewrites external `/v1/*` (the path docs/r5-relay-plan.md's
  HTTP API table specifies) to the `/api/v1/*` functions Vercel's
  file-system routing actually creates.
- `api/cron/retention-purge.ts` is a named `GET` handler (Vercel Cron issues
  GET requests) authenticated by comparing `Authorization: Bearer
  $CRON_SECRET` in constant time (`node:crypto`'s `timingSafeEqual` over a
  SHA-256 digest of each side, so even the length comparison isn't a timing
  side-channel).
- The `pg` pool (`src/db.ts`'s `getPool`) reads `PGPOOL_MAX` (default 10 --
  fine for local dev/tests, including test/race.test.ts's genuinely
  concurrent DB-level race) and `PGPOOL_IDLE_TIMEOUT_MS` (default 30000). A
  serverless deployment should set `PGPOOL_MAX=2` (or 1) and a short idle
  timeout, and point `DATABASE_URL` at **Neon's pooled connection string**
  (the one with `-pooler` in the hostname, routed through PgBouncer) rather
  than Neon's direct connection string, since each function instance should
  hold only a couple of connections at most.

## Privacy

Request bodies, public keys, and identifiers are never logged. HTTP error
responses are always the generic `{ "error": "<code>" }` shape; the adapter
layer (`scripts/dev-server.ts`) logs only a fixed string on an unexpected
adapter-level failure, never request content.
